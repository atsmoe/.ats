  ### 2.4 小字号辅助信息影响桌面阅读

  - **根因**：各页面皮肤独立定义辅助字号，缺少全站最低可读尺寸。
  - **处理**：建立 `--site-min-font-size: 12px`，生产样式统一引用该变量；新增扫描测试，原型文件维持独立评审边界。

2026-9-03 — V2.8.0：FFXIV 编年媒体溯源 · 清晰原图准入

## 1. 本次范围

  为 FFXIV 编年页面补建可审计的图片准入链路。目标是让可见图片同时具备来源证据、唯一事件归属和足够的实际显示清晰度；不符合条件的图片由程序自动隐藏。缩略图仅作为来源比对证据，不参与页面展示。

## 2. 问题、根因与处理

  ### 2.1 既有图片与编年文字之间缺少可验证关系

  - **问题**：历史页面会直接读取本地图片引用，图片、事件正文和来源章节之间没有完整的机器可读证据，容易出现图文不对应。
  - **根因**：早期素材按文件名和人工目录关系接入，未保存 Wiki 页面、章节层级、图片指纹与本地文件之间的绑定关系。
  - **处理**：采集来源页和图片文件页元数据，解析标题层级与图片顺序，建立事件—章节—来源图片—本地候选的映射。匹配同时检查 dHash、平均颜色、长宽比、第二候选差距、文件哈希、尺寸和格式；标题冲突、章节不唯一、指纹不稳定或来源不完整时拒绝准入。

  ### 2.2 小型核验缩略图会造成正式页面发糊

  - **问题**：来源站提供的 128px 缩略图适合快速比对，直接展示会明显损失细节。
  - **根因**：核验证据与访客资源此前没有明确分层。
  - **处理**：缩略图下载目录固定在证据路径，页面数据只接收已通过本地原图检查的记录。构建阶段将可见图片生成 960w WebP，并按实际显示尺寸限制比例；任何需要放大的低清图均自动隐藏。

  ### 2.3 需要控制核验流量且保留失败证据

  - **问题**：来源图片数量较多，批量抓取会带来不可控的流量与中断风险。
  - **根因**：普通抓取脚本通常缺少单文件、批次、重定向、压缩编码和失败发布边界。
  - **处理**：证据缩略图抓取采用串行、identity 编码、禁重定向、15 秒超时、128 KiB 单文件上限和 4 MiB 批次上限。超限文件写入拒绝记录；网络、长度、格式或哈希异常则不发布半成品。此次得到 176 份证据文件、1 个超限拒绝项，共 3,434,319 B。后续原图补齐只触及 36 条高置信来源，每张不超过 8 MiB、总量不超过 32 MiB；实际保存 16 张、7,168,827 B，20 条因 SHA-1 不符自动拒绝。

  ### 2.4 大量事件卡缺少连续阅读节奏

  - **问题**：三个世界的编年数据已经完整，读者仍需逐条打开事件档案；短记录密集、长记录被弹窗打断，难以按章节连续理解因果关系。
  - **根因**：旧界面以单条事件为交互单位，没有面向长篇阅读的章节层、稳定目录和当前位置反馈。
  - **处理**：按各世界资料结构建立独立阅读模型。明日方舟把 876 条记录归入 45 个章节，同日短记录折叠为同期记录，关键节点保持独立锚点；战锤 40K 形成 11 个纪元、31 个章节；FFXIV 将四个分支的 439 条记录编排为 66 个章节。目录、正文、来源和上下文侧栏同时保留，读者可在章节内自然滚动。

  ### 2.5 争议记录与无脚本来源在阅读器投影中丢失

  - **问题**：战锤 40K 的默认覆盖过滤会使 7 条待复核记录退出章节正文；明日方舟大部分记录使用 `prtsSources`，静态页面只读取通用 `sources` 时会丢失来源。
  - **根因**：章节阅读器沿用了旧时间线的发布过滤，无脚本模板也只覆盖较新的来源字段。
  - **处理**：战锤阅读器保留全部 123 条规范记录，7 条待复核项显示“来源争议 / 复核中”，静态页面另设同样可读的争议附录；明日方舟静态模板同时读取两套来源字段。自动测试逐项核对 876、123、439 条记录的唯一性与顺序。

  ### 2.6 浏览器返回与快速分支切换可能串写阅读位置

  - **问题**：明日方舟在阅读器内部跳转时持续写入历史，关闭后可能仍停留在阅读器；FFXIV 切换分支后刷新或返回无法稳定恢复，快速连续切换还可能把上一分支的位置写入当前分支。
  - **根因**：打开阅读器、章节内定位和分支切换共用同一套历史写入策略，延迟保存没有绑定分支与事件快照。
  - **处理**：明日方舟只在进入阅读器时新增一条历史记录，章节与事件定位改为替换当前记录；关闭时一次返回目录。FFXIV 将分支和事件写入 URL 与历史快照，保存任务捕获明确的分支、事件和切换令牌，旧切换回调失效后不再落盘。

  ### 2.7 长页面需要稳定的性能与可访问性边界

  - **问题**：数百条节点持续滚动时，逐帧扫描全部记录会放大主线程开销；阅读器打开后站点导航仍可被焦点访问，离页监听也缺少统一清理。
  - **根因**：原型实现优先验证信息结构，观察器、监听器与焦点隔离尚未收束到完整生命周期。
  - **处理**：明日方舟建立记录索引并使用可见性观察器更新当前位置；三套阅读器统一清理观察器、动画帧、计时器和监听器。打开阅读器时隔离背景导航，FFXIV 与战锤正文改用单一页面主区域下的语义分区，进度条提供读屏数值与文本。

## 3. 验证结果

  - 来源清单：130 条具备完整证据；36 条高置信映射进入原图核验，16 条通过；114 条自动隐藏。原有本地预览副本全部退出准入路径。
  - 页面产物：16 张可见图片均为站内、SHA-1 与来源元数据一致的原图，外链数 0、缩略图 URL 数 0、预览副本数 0。构建保留其原始字节，不替换为低清 WebP。
  - 自动测试：FFXIV 媒体专项覆盖来源、缩略图证据、原图下载边界、哈希、尺寸和页面准入；Windows 软链接创建用例会因系统权限跳过。
  - 数据校验：三世界数据校验通过；正式构建完成媒体处理与产物写入。

  - 自动测试：354 项通过，1 项因 Windows 无法创建测试符号链接而按预期跳过；数据校验与差异检查通过。
  - 浏览器实测：三页目录、章节打开、进度、关闭返回、FFXIV 四分支切换与浏览器返回均符合预期，控制台无错误。
  - 本轮纳入统一验收，准备普通推送；共享工作树里的旧原型发布边界仍按白名单处理。

2026-6-29 — V2.5.1：滚动性能修复 · 重复处理器清理

## 1. 诊断过程

  V2.5.0 上线后用户反馈页面浏览比之前卡顿。三个 Explore agent 并行排查：
  - Agent A：追踪正常页面加载路径（main.js → timeline-ui.js → portal-transition.js → data-loader.js → virtual-timeline.js）
  - Agent B：检查构建产物（bundle.js 体积、图片输出、HTML script 加载顺序、CSS 动画开销）
  - Agent C：审计滚动渲染性能（scroll handler 效率、_renderRange 节点管理、RAF 调度、合成层压力）

## 2. 根因：重复滚动处理器

  发现 `window` 上注册了两个内容完全重复的 scroll 事件监听器：

  | 位置 | 节流 | 每次滚动执行 |
  |------|------|-------------|
  | `virtual-timeline.js:346` | 无节流 | `VirtualTimeline.update()` + `updateEraNavHighlight()` + `updateBackToTop()` |
  | `timeline-ui.js:446` | RAF 节流 | 同上三件事 |

  每次滚动事件触发时：
  - virtual-timeline.js 同步执行 `updateEraNavHighlight()` → `VirtualTimeline.items.filter(item => item.type === 'era-header')` 遍历全部 876 items
  - timeline-ui.js 在下一 RAF 帧再次执行相同逻辑
  - 每帧滚动 = `updateEraNavHighlight()` 执行两次 = **876 × 2 = 1752 次迭代** + 两次 `querySelectorAll` + 两次 `forEach` DOM 操作

  V2.5.0 自身的 JS 改动全都不在正常滚动路径上（portal 逻辑只在带 hash 时执行，fetchWithRetry 成功路径零开销，图片渲染仅在弹窗打开时触发），但预存的重复处理器问题被充分暴露。

## 3. 修复方案

  ### 3.1 移除 virtual-timeline.js 的 scroll handler
  - 删除第 346-352 行的 `window.addEventListener('scroll', ...)` 
  - 保留 resize handler 不变（timeline-ui.js 没有 resize handler）
  - timeline-ui.js 的 RAF 节流版本独自承担滚动处理

  ### 3.2 清除 window.renderEvents 死代码
  - `window.renderEvents`（第 493-515 行）内部调用 `getBranchEvents(branch)`，该函数是 timeline-ui.js 的 ES module 导出，不在全局作用域 → 调用即抛 `ReferenceError`
  - V2.5.0 已移除 portal 动画完成回调中的唯一调用点
  - 将 `renderEventsDirect()` 保留为 `VirtualTimeline._renderEventsDirect` 备未来使用

## 4. 附带发现（未修复，留待后续）

  - `_renderRange()` 每次范围变化时通过 `querySelectorAll` + `el.remove()` 销毁全部 ~15 个可见节点，再从 `_buildNode()` 重建。`nodePool` Map 已声明但从未用于节点回收——死数据结构
  - `_renderRange()` 在渲染前 O(n) 扫描 range.start 前所有 item 以计算事件索引（交替左/右侧）
  - 每个 `.event-card` 使用 `backdrop-filter: blur(8px)`——15 个可见卡片 = 15 个背景滤镜合成层，在低端设备上造成 GPU 压力
  - 3 处 `transition: all` 可收紧为具体属性

  - dist 产物确认：scroll handler 已从 virtual-timeline.js 移除，`window.renderEvents` 不存在

- 导航高亮：nav.njk 中通过 {% if worldId === 'arknights' %} 等判断加 .active 类

## 5. JS 模块化细节

- 源码使用 ES modules（import/export）
- esbuild 打包为 IIFE 格式 dist/js/bundle.js（62KB），virtual-timeline.js 单独复制
- BackgroundManager 从 hardcode getElementById 改为 init(canvasId, videoId, imageId) 模式

- 到达侧：initPortalArrival 检测 location.hash → 在数据中搜索目标事件 → 直接 VirtualTimeline.load() + estimateScrollTopByEventId() 预估定位 → update() + remeasure 校正 → 反向收束动画 → dismissPortal（无需全量渲染，无二次加载）

## 7. 传送门过渡（Portal Transition）

出发侧：
  1. 用户点击 .cross-world-link（e.preventDefault）
  2. 以点击坐标为圆心，Canvas 涡旋粒子向外螺旋扩散
  3. 光晕完全不透明时 → window.location.href = targetUrl

到达侧：
  1. #portal-arrival 内联 div 从 HTML 解析第一刻遮住全屏（#060a14 深空底色）
  2. 读取 window.__WORLD_DATA__（内联数据，瞬时可用）
  3. 解析 location.hash 得到目标事件 ID
  4. 临时关闭虚拟滚动 → 全量渲染所有节点
  5. scrollTo + requestAnimationFrame 等待目标节点
  6. 播放反向收束动画（Canvas 粒子 + 光晕收缩到目标位置，~400ms）
  7. 移除遮罩，恢复虚拟滚动
